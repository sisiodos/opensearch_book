# 第6章 改訂記録

改訂日：2026-10-03

第6章では、検索ドキュメントの内部で、属性どうしの関係をどこまで保持するかを学びます。初学者が「なぜこの構造を選ぶのか」を理解できるよう、移動区間の検索例から object と nested の違いを説明し、検索条件に合わせて構造を選ぶ視点を重視しています。

改訂内容を、用語・説明などの訂正（errata）と、説明の充実・整理や選択肢の追加（revised）に分類しています。

今回の改訂では、OpenSearch 2.7 で導入された `flat_object` を、フィールド数爆発への対策となる設計の選択肢に取り入れています。また、本書の設計方針を、`nested` の利用をできる限り避ける方針から、検索・集計で同じ配列要素内の属性の対応を保持する必要がある場合に、`nested` を正当な選択肢として受容する方針へ変更しています。不要な場合は、より単純な構造を選びます。この変更は本書の説明・設計方針の見直しです。`nested` は OpenSearch 1.0 から提供されており、2.7 で非推奨から推奨に変わったという製品側の変更を示すものではありません。

## errata

| 節 | 改訂後の内容 |
| --- | --- |
| 6.1.1 object の属性と配列 | 単一オブジェクトの属性を同じドキュメント内で検索する場合と、オブジェクト配列の要素ごとの対応を検索する場合を分けて説明しています。 |
| 6.1.2 フィールド数の増加 | 同じ属性を持つレコードの追加と、新しいキーの追加を区別し、動的なキーがマッピングフィールドとして増える仕組みを説明しています。 |
| 6.1.3 階層とフィールド数 | JSON の階層を浅くしても、属性の種類が同じなら末端のフィールド種類数は減らないことを説明しています。 |
| 6.2.1 nested の実装 | 各要素を hidden Lucene document として索引し、Lucene の block join を使って検索結果を親へ結び付ける仕組みを説明しています。 |
| 6.2.5 nested とフィールド数 | 要素ごとの関係を保持することと、キーの種類数を管理することを、別の設計課題として説明しています。 |
| 6.2.2 / 6.2.6 関係の保持 | nested が同じ要素内の属性を同じ検索スコープで評価することを説明し、データ登録時に扱う参照整合性との役割を分けています。 |

| 6.1.3 flat_object（version update） | OpenSearch 2.7 で導入された flat_object を、多数・動的なキーによるフィールド数爆発への対策として紹介しています。取得・表示中心の用途と、数値比較や内部属性の集計などの制約を説明しています。 |
| 6.2.2 nested クエリ | 同じ区間の条件を一つの nested クエリ内にまとめ、要素内で一致を判断して親ドキュメントを返す流れを説明しています。 |

| 6.2.4 配列と構造の選択 | keyword の配列、object の配列、nested を、検索で必要な関係の違いから段階的に説明しています。 |
| 6.2.5 nested の採用方針とコスト | nested をできる限り避ける方針から、要素内の関係が必要な場合に受容する方針へ変更しています。関係の必要性を起点に nested を選び、内部ドキュメント数の増加と検索・集計の処理を確認する視点を示しています。深さ・nested フィールドの種類数・要素数の上限設定を分けて紹介し、要素数の多いデータで検索・集計・更新の負荷を確認する方法を説明しています。 |
| 6.2.6 フラット化の整理 | object のフィールド展開、アプリケーション側の flatten、flat_object フィールド型の役割を分けて説明しています。 |
| 6.2.6 設計原則 | JSON の見た目や階層の深さよりも、検索時にどの関係を保持する必要があるかを基準に構造を選ぶ指針を示しています。 |
